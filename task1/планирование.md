# Планирование: анализ, идентификация проблем и поиск решений

## 1. Проблемные места

Ниже список проблемных мест системы Александрит. Первые два проблемных места сразу хотелось бы выделить как самые важные, т.к. решив их, можно снять самую острую боль бизнеса и пользователей. Затем можно в уже более спокойном режиме приступить к решению остальных проблем.

1. Система не справляется с расчётом стоимости новых заказов, поступающих по разным каналам. Фактически пропускная способность системы ограничена. Возможно потребуется выделение модуля, который будет заниматься исключительно рассчётами, чтобы его можно изолированно масштабировать. Решив эту проблему, бизнес сможет получать выгоду, которую сейчас недополучает из-за недостаточной загруженности производственных мощностей.
2. Второй по важности хотелось бы выделить проблему неудовлетворённости пользователей из-за "тормозов" в прогрузке списка заказов и при выполнении других действий в CRM. В частности корнем проблемы может быть использование только 1 инстанса для каждого компонента Александрит а также использование БД одновременно как на запись так и не чтение. Последнее затрудняет оптимизацию работы БД. Навешивание излишних индексов на таблицы с целью ускорить чтение может негативно сказаться на записи изменений, т.к. потребуется время на пересчёт индеков.
3. В системе никак не разграничивается анализ сложных и простых моделей (при расчёте стоимости). Необходимо получить статистику кол-ва сложных и несложных моделей и какие из низ приносят наибольшую прибыль. Также нужно проверить возможность быстро определять сложность модели чтобы отделять модели по сложности на этапе передачи в процессинг. В итоге, разграничение моделей по сложности позволит принять более эффективные меры по ускорению процессинга.
4. В CRM только один сервис который обрабатывает и заказы и разных систем (онлайн магазин и MES) и управление производством (когда продавец подтверждает заказ). Необходимо провести анализ и обозначить чёткие зоны ответственности сервисов в целевой архитектуре.
5. На подумать: может поменять брокер с RabbitMQ на Kafka

## Инициативы для устранения нежелательных ситуаций

1. настроить автоматический запуск дополнительных инстансов на случай увеличения нагрузки
2. разделить хранилища отдельно для чтение и для записи. Возможно применить CQRS подход.
3. применить кэширование (подумать на какие запросы и как)
   1. рассмотреть вариант с read-through и write-through + программная инвалидация кэша чтоб у всех было корректное представление о статусе заказов (при чём эффективнее делать инвалидацию по ключу)
4. разделить UI интерфейсы для активных и завершённых заказов. Участникам как правило интересно увидеть только новые заказы чтоб взять их в работу.
5. разделить сервисы CRM по зонам ответствнности чтоб можно было масштабироваться
6. улучшить мониторинг чтобы лучше информировать пользователей в случае ошибок (у человека не должно возникать неопределённости что произошло)
7. где применимо, сделать побольше асинхронных вызовов на бэке чтоб ответ клиенту приходил быстрее и клиент не ждал пока отработает фоновый тяжёлый процессинг.
