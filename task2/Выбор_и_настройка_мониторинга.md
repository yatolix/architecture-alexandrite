# Выбор и настройка мониторинга в системе Александрит

## Мотивация

Добавление мониторинга в систему позволит быстро реагировать на события в работе системы. При чём речь как о технических событиях, когда что-то сломалось или резко возросла нагрузка, так и о бизнесовых событиях - упал % заказов от общего числа посетителей, увеличилось среднее время обработки заказа и т.д.

Мониторинг тем самым поможет принимать решения заблаговременно, минимизируя недовольство пользователей. Особенно это критично для новых посетителей. По статистике, более 30% посетителей уже никогда не возвращаются на сайт если у них был первый плохой опыт взаимодействия с сервисом. Для ювелирной индустрии процент "невозвращенцев" оценивается даже больше из-за высоких ожиданий посетителей. Человек принял, возможно, и так непростое для себя решение выложить крупную сумму за украшение, и, в случае неудачи, его разочарование будет гораздо больше, чем если он просто не смог заказать очередную безделушку на маркетплейсе. Кроме того, кому как не бизнесу понимать, что потеря потенциального клиента стоит по разным данным в 5-25 раз дороже чем сохранение существущего.

Учитывая всё вышеизложенное, предлагается определить набор самых критичных метрик для мониторинга и внедрить их.

## Выбор подхода к мониторингу

Учитывая, что проблемные места системы в разных сервисах, предлагается использовать разные подходы к мониторингу, которые наиболее подходят для каждого проблемного места.

1. В MES API предлагается использовать подход USE. Производительность этого сервиса замедляется при увеличении количества заказов - сервис не справляется с расчётом стоимости изделий. Метод USE позволит понять насколько эффективно утилизируются ресурсы (Utilization), объём заказов, которые сервис не успевает обработать (Saturation), а также возникающие ошибки (Errors).
2. Для интернет магазина и CRM (только CRM - не API) предлагается использовать метод Четырёх золотых сигналов. Метод подходит для отслеживания запросов и позволит понять есть ли какие то задержки, какова частота неудачных запросов.
3. Для CRM API предлагается использовать метод RED. CRM API используется из разных частей системы, на нём много ответственности, поэтому важно отслеживать его пропускную способность. Собранные метрики также очень помогут в принятии будущих архитектурных решений по части разделения сервиса на отдельные удобно поддерживаемые модули, которые кроме того можно будет независимо друг от друга масштабировать.
   Также метод RED может пригодиться для Messages Queue т.к. наличие проблем в очереди может быть важным индикатором что система не справляется и необходимо принять меры.

## Список метрик

1. Для MES API:
   * % использования CPU и RAM- это классическая инфраструктурная метрика которая позволит следить за общим состоянием сервиса
   * процент потоков занятых расчётом стоимости изделий к общему проценту потоков - метрика поможет понять насколько процессы рассчёта стоимости забивают систему и сколько остаётся свободных воркеров для других задач
   * количество неуспешных расчётов стоимости изделий (за час) - метрика даёт общую картину о том сколько посетителей не смогли получить расчёт. Метрика может быть полезна когда начнём внедрять auto-scaling. Посмотрим как это повлияет на динамику ошибок.
     ярлык: error_type (timeout|system)
   * среднее время рассчёта стоимости (сегментированное по сложности изделия). Из этой метрики сможем понять как долго клиенты ждут рассчётов в зависимости от сложности изделия.
     ярлык: complexity (low|meduim|high)
   * кол-во вызовов API за час в разрезе партнёров. Метрика поможет понять какие партнёры больше всего используют нашу систему.
     ярлык: partner_id
2. Для CRM:
   * время загрузки списка заказов по 95-му перцентелю. Метрика нужна чтобы косвенно отслеживать удовлётворённость пользователей при работе со списком заказов. Если 95% пользователей открывают список менее чем за 3 сек. - это хорошо. Но если время возрастает, то нужно предпринимать меры.
     ярлык: page (orders_list)
   * % заказов с просроченными сроками поставки
     ярлык: order_delay (>5, >10, >20)
     можно ещё добавить ярлык по типу клиентов (прямые или через партнёров)
   * среднее время обработки заказа (от создания до того как взяли в производство)
     ярлык: order_status (INITIATED, ..., MANUFACTURING_STARTED)
   * соотношение роста новых заказов к росту жалоб. Метрика поможет понять насколько растёт недовольство клиентов с ростом количества заказов.
   * Для CRM API: кол-во входящих запросов в секунду
   * Потери дохода из-за отменённых заказов в месяц
3. Для RabbitMQ:
   * соотношение опубликованных сообщений к обработанным за период времени (скорее всего за час, т.к. за секунду мы не получим корректной картины - заказы всё таки приходят не так часто)
   * ошибки недоставленных сообщений
   * средняя задержка обработки сообщений
