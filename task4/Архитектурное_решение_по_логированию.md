# Архитектурное решение по логированию

## Список логов с уровнем INFO

* Shop API: создание черновика заказа. Логируем время, идентификатор клиента, основные опции заказа выбранные клиентом
* Shop API: загрузка 3d файла. Логируем время, наименование файла, размер файла
* CRM API: подтверждение производства. Логируем время, идентификатор заказа, идентификатор сотрудника
* CRM API: создание нового заказа от партнёров. Логируем время, идентификатор заказа, идентификатор сообщения из RabbitMQ, идентификатор клиента и партнёра
* MES API: запрос списка заказов. Логируем время, фильтры, идентификатор оператора
* MES API: вычисление стоимости заказа. Логируем время, идентификатор заказа, идентификатор 3D файла

Помимо INFO также необходимо использовать другие уровни логирования.

DEBUG - для более детального разбора проблем. Например, пошаговый лог сохранения 3D файла. Пошаговый лог вычисления цены. Пошаговый лог парсинга сообщения из очереди и создания заказа.

ERROR - отлавливать и логировать ошибки на более высоких уровнях абстракции чтобы дать более понятное объяснение что произошло:  не удалось создать заказ, не удалось рассчитать цену и т.п. Ошибки не должны быть сполшным stack trace-ом с низкоуровневыми техническими деталями.

## Мотивация

Логирование позволит тратить меньше времени на локализацию ошибок системы. Также сотрудники поддержки смогут быстрее находить причины произошедшего, особенно если будет возможность переключаться на более детальный уровень логирования.

Логирование может повлиять на такие метрики как:

* среднюю скорость обработки заказов (если получится за счёт логирования быстрее находить причины застревания заказов и продвигать их дальше по жизненному циклу)
* удовлетворённость клиентов и, как следствие, уменьшение жалоб. Благодаря логированию будет возможность исправить проблемы ещё до обнаружения их клиентами.
* с помощью логов может удастся отследить медленные запросы при запросе списка заказов

В первую очередь необходимо настраивать логирование для CRM API, Shop API и MES API - это бэкенд компоненты которые делают основную работу. Почти весь жизненный цикл заказов проходит через них. Начав внедрение логирование с этих трёх компонентов мы быстрее доберёмся до корневых причин проблем связанных с медленной обработкой заказов.

### Политика безопасности

К логам будут иметь доступ следующие категории сотрудников:

* Офицеры безопасники, роль Security Admin, полный доступ к логам и управлению
* DevOps инженеры, могут смотреть и создавать дэшборды а также настраивать алерты на события.
* Сотрудник поддержки, могут смотреть и выборочно создавать дэшборды с логами.
* MES Оператор, может смотреть только MES логи
* Аудитор, может смотреть логи аудита
* Разработчики и QA, доступ к чтению всех логов на тестовых средах и временный доступ по согласованию с менеджментом и безопасниками на ПРОД, но для под конкретные цели.

Чувствительные данные в логах будут маскироваться. Никаких перс. данных в логах или платёжной информации.

Доступ к логам - только из-под корпоративного VPN или из внутренней сети офисов.

### Политика хранения

* Лог файлы разделять по уровням логирования (INFO, ERROR, WARN)
* Каждый день создавать новые файлы
* Сроки хранения
  * ERROR - хранить дольше всех, от 12 до 18 месяцев чтобы можно было провести пост анализ ошибок.
  * WARN - хранить около 6 месяцев. Иногда нужен анализ чтоб исправить некритичные предупрежедения. Невсегда до них сразу доходят руки, поэтому важно чтоб они хранились какое-то время если вдруг возьмут задачу по их исправению из техдолга.
  * INFO/DEBUG - макс. 1 месяц. Логи нужны для оперативного реагирования на проблемы.
* Размеры индексов в разрезе уровней логирования
  * ERROR: 50GB - т.к. дольше всех хранятся и анализ требуется нечасто.
  * WARN: 20GB - что-то среднеевзешанное чтоб не плодить много файлов, в то же время чтоб поиск по логам не затягивался.
  * INFO/DEBUG: 10GB - нужен быстрый поиск по файлам в случае расследования поведения системы.
* Учесть нормативные требования - возможно отдельные логи нужно будет хранить до 5 лет.
* При удалении логов делать снапшоты в виде файлов в S3.

### Мероприятия по анализу и поиску аномалий

1. На самые критичные события необходимо настроить алертинг команды поддержки по SMS. Например, если начали падать заказы с ошибками или нарушилась интеграция (нет подключения к брокеру сообщений), или найдены попытки взлома системы, или произошла резкая сильная деградация производительности (среднее время запросов увеличилось в 3х раза).
2. Для менее критичных событий можно слать алерты в группу поддержку по корп. менеджеру,ю например в Slack. Например, когда увеличилось среднее время расчёта стоимости или возник резкий рост ошибок в логах.
3. В будущем сделать интеграцию с системой инцидент менеджмента (например в JIRA) чтобы автоматически создавались тикеты на расследование с приложенными логами проблемы.
